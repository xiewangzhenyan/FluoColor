## 1. 结论

当前 Android 工程已经实现了可运行的 PG-Grid/PG-Quant 主链，在冻结的 10×10、
15×15 和后台兼容 4×4 合成样例上具有较好的数值一致性和端侧性能；但不能称为
“完美实现了参考目录全部内容”。

主要原因有四类：

1. Android 定位器是同一科学契约下的重新实现，不是 Python 的逐算法等价移植；规则轴选择、局部精修、单应拟合细节和候选支撑距离存在差异。
2. Android 尚未建立与 Python `pg_benchmark.py` 等价的七扰动族端侧退化曲线，现有同图一致性测试主要使用合成干净样例。
3. Python 的帧级曝光、模糊、光照均匀性等 QC 没有完整接入当前微流控协调器的重拍门控。
4. 用户界面只展示阶段文字和完成后的最终原图定位/结果热力图，没有展示矫正图、ROI/背景环、平场校正或定位中间证据。

因此准确表述应为：**核心主链已实现并通过合成金标准容差验证，但算法等价性、真实复杂场景覆盖和可视化证据链仍不完整。**

## 4. 关于“畸变矫正”的准确表述

当前微流控 PG-Grid 主链中的 `rectifyChip()` 是基于四角的 8 自由度单应变换，解决的
是平面芯片的旋转、缩放、剪切和透视视角问题。它不等于基于相机内参和畸变系数的
镜头径向/切向畸变校正。

项目旧 `ImageCorrectionViewModel` 中确实存在估计 `k1/k2` 并调用 OpenCV
`Calib3d.undistort()` 的代码，但当前直接新建项目会直接进入 `WellDetection`，微流控
网关明确绕过旧 `DetectionViewModel`；PG-Grid 协调器没有调用旧图像矫正页面。因此：

- 旧孔板链路可能展示“原图/矫正图”；
- 当前直接微流控 PG-Grid 链路没有使用或展示该径向畸变校正；
- Python V2 设计本身也明确把径向项 `k1` 暂缓，等待扰动基准证明其可辨识性。

在正式接通并验证前，微流控页面应使用“透视矫正”或“视角校正”，不应笼统宣传为
“镜头畸变矫正”。

## 5. 用户当前能看到什么

### 5.1 处理中

`GridDetectionGatewayContent` 当前只显示：

- 圆形进度指示器；
- “检查项目配置、定位芯片并校正视角、提取逐位点信号、检查模型、保存结果”等阶段文字；
- 一段保持页面开启的通用说明。

没有实时或阶段性图像。定位在虚拟机上的 P95 只有约 `76～258 ms`，多个状态可能很快
连续切换，用户甚至不一定能清楚看到每一个阶段文字。

### 5.2 完成后

结果页已经具备：

- 可靠性/主特征/浓度热力图；
- 位点详情、定位来源、置信度和 QC 原因；
- 原图上的冻结定位圆点；
- 候选精修、模型补位、未平差、质量失败的颜色图例；
- 标签和显示增强开关。

这能让用户核对最终点位是否落在正确位置，但仍看不到算法处理过程本身。

### 5.3 当前缺少的可视化证据

- 原图芯片四角和检测区域；
- 透视矫正前后对比；
- black-hat/top-hat 候选点；
- 初始晶格与平差后晶格对比；
- 圆形信号 ROI 和背景环；
- 原始信号与平场校正信号对比；
- 光照场/平场模型；
- SNR 热力图；
- 校正颜色分布图；
- 每个处理阶段的完成状态和可追溯预览。

此外，当前 `CaptureArtifact` 只保存原图路径，`derivedPath` 没有写入；矫正图和诊断图
不会进入历史结果或导出归档。

## 6. 建议的后续优先级

### P0：补齐可追溯的处理证据链

1. 在结果页新增“处理过程”标签，而不是让高速算法为了动画被人为延迟。
2. 保存或按冻结参数重建：原图区域、透视矫正图、定位叠加、ROI/背景环、平场诊断。
3. 所有派生图明确标记“仅用于显示/诊断”，定量继续从原始图反投影采样。
4. 处理中页面使用步骤时间线和最近完成阶段的缩略图；处理过快时直接进入完整证据页。

### P0：补齐帧级图像质量门控

把曝光、欠曝、模糊、光照不均和过度透视真正接入 `GridDetectionCoordinator` 的
`RetakeRequired` 判断，不能只依赖候选支撑率和补位比例。

### P1：建立 Android 扰动退化曲线

将 Python 已有的旋转、透视、模糊、光照梯度、遮挡、高光和噪声七族确定性场景导出为
Android 测试语料；同时比较定位误差、来源分类、支撑率、光度秩相关和可靠位点比例。

### P1：处理定位实现差异

优先评估以下差异是否造成真实图回归，再决定严格移植还是保留 Android 变体：

1. 规则轴组合搜索与加权 k-means 的差异；
2. 10×10 专用方形组件精修缺失；
3. 完整两轮局部观测重采样缺失；
4. 候选支撑距离 `0.42 pitch` 与参考 `0.25 pitch` 的差异；
5. Tukey 稳健尺度下限与 DLT 参数化差异。

### P2：镜头畸变校正

在没有相机内参或可信可辨识性验证时，不建议把旧启发式 `k1/k2` 直接并入科学主链。
应先建立设备标定或确定性径向畸变基准，再决定启用相机内参校正或继续只做透视矫正。

## 8. 用户实拍兼容修复与 Android 迁移边界

### 8.1 实拍失败根因

用户提供的 2 张 10×10 与 4 张 15×15 EL 背光实拍图均为“亮背景上的暗单元”。旧 Android
直接新建逻辑却把 15×15 的 `targetPolarity` 写成 `BRIGHT`，定位器也把这个配置当作硬约束，
导致真实 15×15 图片按亮点查找时支撑率降为 0。与此同时，协调器把任何帧级 `FAILURE` 都直接
转成 `RetakeRequired`；即使 10×10 图片已经形成支撑率 `0.91/0.77` 的可信晶格，也会因曝光、
光照或透视阈值被强制退回“需要重新拍摄”。

### 8.2 已实施修复

- 定位器同时提取暗目标和亮目标候选，依次使用候选数量与理论位点数的吻合度、内部灰度均值/中位数
  提示、候选轴和稳健单应是否真正成立来裁决极性；载体旧极性只作为最终平局偏好。
- 直接新建 15×15 的兼容默认值修正为 `DARK`，避免运行快照和日志继续传播错误语义。
- 帧级 QC 继续完整持久化，但不再因为保守图像阈值隐藏已经生成的测量和热力图。真正不可计算的
  图片解码失败、定位异常或坐标契约损坏仍由异常/契约校验阻止。
- 完成页明确提示“质量风险已记录但结果已保留”，结果页可同时查看总览、分析物、原图、九步过程
  和质控原因，由用户决定是否需要重拍。

### 8.3 固定实拍回归与设备验收

六张原始 JPEG 已按字节不变方式复制到 `app/src/androidTest/assets/pg_grid/real_v1/images/`，仅将文件名
改为 ASCII；`manifest.json` 记录原始文件名、SHA-256、规格、Python 极性、支撑率和质量状态。
设备测试故意继续给 15×15 传入旧 `BRIGHT` 偏好，验证图像证据仍会覆盖旧配置。最终六张均自动
裁决为 `DARK`，Android 支撑率为 `0.91 / 0.77 / 1.0 / 1.0 / 1.0 / 0.924444`，全部形成完整可信晶格。

在 `emulator-5554` 中通过系统 Files 从 Download 导入真实 `1.jpg`，完成 15×15 生产流程：保存
`225/225` 位点，得到 `211` 个可靠结果，不再出现强制重拍页；原图定位叠加、最终晶格和九步处理过程
均可见。相关截图位于 `docs/superpowers/plans/screenshots/real-15x15-*.png`。

### 8.4 仍未完成的迁移事项

当前 Android 算法核心仍是 Kotlin + OpenCV Java API，并非 `android_migration.md` 推荐的 C++ 核心、
薄 JNI JSON 边界和 Kotlin/Compose 应用层。工程中尚无桌面 C++ parity、CMake/NDK 核心或
`libpggrid.so`；Android OpenCV 仍为 4.5.3，也未与参考端锁定到建议的 4.9+。此外，目前只实现了
单元极性自动识别，网格规格仍由项目的 `rows × columns` 提供，尚未自动并行尝试 10×10/15×15。

因此当前准确结论是：**最严重的实拍极性错误和强制重拍问题已经解决，首批真实芯片已进入固定回归；
但 C++/JNI 正式迁移、OpenCV 版本对齐、规格自动识别和多设备实验室金标准仍需作为后续独立工作包完成。**
